## Precondition — real local packages, not real NuGet.org packages yet

`Antiphon`'s NuGet packages are **not published to nuget.org yet** (that's blocked on this very
phase plus EULA review — see `ecosystem/ACTIVE_PRIORITIES.md` in Wolfgang). So these samples can't
literally `dotnet restore` from nuget.org today. Instead, they build against a **local package
feed** produced by the private repo's own release-packing script:

1. In `../Antiphon` (read-only for this phase — do not edit anything there), confirm
   `tools/pack-release.sh` has been run recently, or run it yourself:
   ```bash
   AntiphonStrongNameKeyFile=<path to the real .snk, ask the user if you don't have it> \
     tools/pack-release.sh 2026-09-03T00:00:00Z
   ```
   This produces `.nupkg`/`.snupkg` files under each `src/<Project>/bin/Release/` in `../Antiphon`.
2. In `antiphon-examples`, add a `NuGet.config` at the repo root pointing a local feed source at
   that output (a `<packageSources>` entry with a relative or absolute path to
   `../Antiphon/src/*/bin/Release/`, or copy the built packages into a `local-feed/` folder inside
   `antiphon-examples` itself if you'd rather the repo be self-contained and not depend on a sibling
   checkout existing — **prefer the self-contained copy approach**, since anyone cloning
   `antiphon-examples` alone should be able to build it; document clearly in the README that this is
   a **pre-release local-feed setup**, and that once real packages are live on nuget.org, the
   `NuGet.config`'s local source should be removed and `PackageReference` versions pinned to the
   real published version instead — leave that as a named follow-up, don't attempt it now since
   nothing is published yet).
3. `local-feed/` (or wherever the copied packages land) should be **`.gitignore`d** — do not commit
   built `.nupkg` binaries into the public repo; the README's setup instructions should tell a
   contributor how to regenerate them (i.e., "build `Antiphon` from source, run its
   `pack-release.sh`, copy the output here" — a private-repo-access precondition worth stating
   plainly, since public visitors without access to `Antiphon` won't be able to build these samples
   until real NuGet packages exist; note this limitation honestly in the README rather than hiding
   it).

### 2. `01-generate-xrechnung/` — Scenario 1

Wrap the getting-started doc's Scenario 1 code into a real console app: build the `Invoice`, call
`UblInvoiceGenerator.GenerateXml`, write `invoice.xml` to the current directory, and print a short
confirmation (`"Wrote invoice.xml ({n} bytes)"`) plus a one-line reminder that generation is
deterministic (byte-identical output on repeat runs — matches the doc's own claim).

### 3. `02-validate-peppol/` — Scenario 2

Needs an actual sample Peppol BIS Billing 3.0 XML document to validate against, since the doc's
scenario reads `invoice.xml` from disk rather than generating it inline. Two options, your call based
on what's cleanest: (a) generate a valid Peppol-profile invoice programmatically at the top of
`Program.cs` using the same `UblInvoiceGenerator` from Scenario 1 with `SpecificationIdentifier` set
to the Peppol BIS URN (check `docs/Antiphon-Rule-Engine.md` in the private repo for the exact URN
string if the getting-started doc doesn't have it), then validate that in-memory output — this makes
the sample fully self-contained with no external file dependency; or (b) commit a static
`sample-invoice.xml` fabricated Peppol document alongside the project. **Prefer (a)** if it's not
significantly more code — a self-contained "generate then validate" sample is a stronger
demonstration than "validate this file we handed you." If you go with (a), rename the folder/scenario
framing appropriately in its README (e.g. "Scenario 2: Validate a Peppol BIS Billing 3.0 invoice"
still holds even if you also generate it first — the validation call is still the point).

Wire up `RuleSetCatalog.Discover()` → `LayeredValidator.Validate` exactly as documented, print
well-formedness/schema/violations/provenance to the console.

### 4. `03-facturx-pdf/` — Scenario 3

Needs a real, minimal PDF/A-conformant seed PDF to embed into (the doc's precondition: Antiphon adds
the Factur-X layer, it doesn't convert an arbitrary PDF to PDF/A). Produce or source a small,
genuinely PDF/A-1 or PDF/A-3 conformant single-page PDF (a minimal "Invoice" placeholder page is
fine — content doesn't matter, conformance does) and commit it as `sample-input.pdf`. If you can't
produce a verifiably-conformant PDF/A file within this phase's scope, **stop and report it** rather
than committing a PDF that merely claims conformance without verification — this is exactly the kind
of thing that would embarrassingly fail for the first real evaluator who runs the sample.

Wrap the doc's Scenario 3 code: build the `Invoice`, `CiiInvoiceGenerator.GenerateXml`, read the
seed PDF, `FacturXEmbedder.Embed`, write `facturx-output.pdf`, then round-trip with
`FacturXExtractor.Extract` and print `"round-trip OK"` or the mismatch, exactly as documented.
